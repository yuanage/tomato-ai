# 番茄AI · 数据持久化方案（任务/番茄记录/设置/AI 状态）

> 版本：v0.1.8 · 状态：已实施并测试通过
> 解决的问题：**清理后台任务（杀进程）后任务数据全部丢失**

---

## 一、问题分析（根因）

### 1.1 现场现象
- 添加任务 → 应用退到后台 → 从最近任务列表划掉（进程被杀）→ 重新打开 → **任务全部消失**。
- 正常关闭/切页不丢；统计、设置同源存储，风险一致。

### 1.2 代码层排查结论（排除项）
逐一审计本地存储实现，**不存在以下逻辑缺陷**：
| 常见缺陷 | 本项目情况 |
|---|---|
| 防抖/延迟批量写 | ❌ 无。每次变更立即 `persist()` 并 await（写透式） |
| 读空覆盖写（load 失败当空表） | ❌ 无。`ensureLoaded` 失败即抛错，不产生空表覆盖 |
| 键名冲突/版本漂移 | ❌ 无。`localforage.config` 名称固定（tomato-ai / tomato_ai_data），键名固定 |
| 全局 clear 误触发 | ❌ 无。仅设置页"清空本地数据"显式触发 |

### 1.3 环境层根因（结论）
数据存储在 **安卓 WebView 的 IndexedDB**（localforage 默认后端）里，其落盘由 WebView 进程管理。已知问题类：
- **硬杀进程**（从最近任务划掉）时 WebView 不保证触发 `pagehide`/`beforeunload` 等清理回调；
- IndexedDB 的 leveldb 数据在进程被杀时可能**未完成 checkpoint**，或重启后**打开失败/读回空**；
- 个别 ROM 激进回收会重置 WebView 数据目录。

→ 表现即为：进程存活期间一切正常，进程被杀后 IndexedDB 读回空 → 界面显示"全部丢失"。

### 1.4 次级风险（本方案一并修复）
1. **fire-and-forget 写窗口**：`TasksView.handleAdd`、`HomeView` 落库等调用未 await，进程恰在写入途中被杀时该次写丢失；
2. **AI 状态存 localStorage**：与 IndexedDB 同属 WebView 存储，一样不可靠；
3. **无镜像/无恢复路径**：IndexedDB 损坏后没有任何补救手段。

---

## 二、存储技术选型

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| localStorage | 简单、同步 | 同属 WebView 存储，杀进程同样不可靠；容量 5MB；同步阻塞 | 淘汰（仅作降级参考） |
| IndexedDB（localforage） | 容量大、异步、现有代码已用 | **进程被杀后不可靠**（见 1.3） | 保留为主通道 |
| **文件系统（Tauri 原生命令）** | 纯文件落盘，**不随 WebView 存储重置**；写入即持久 | 需少量 Rust 代码；网页预览环境不可用 | 采用为镜像通道 |

**结论：IndexedDB（主通道，网页预览兼容）+ 应用数据目录文件镜像（可靠性通道，Tauri 环境）双写。**
Rust 侧仅 3 个 `#[tauri::command]`（fs_save / fs_load / fs_remove），零第三方依赖，符合"最小依赖"约束。

---

## 三、数据结构与存储策略

### 3.1 存储键（4 类数据，与 Rust 白名单一致）
| 键 | 内容 | 结构 |
|---|---|---|
| `tasks` | 任务清单 | 任务对象数组 |
| `pomodoro_records` | 番茄完成记录 | 记录对象数组 |
| `settings` | 应用设置 | 对象（缺省合并） |
| `ai_agent_state` | AI 助手结果/输入 | 对象快照 |

### 3.2 文件镜像信封（仅文件侧）
```
{ "v": 1, "savedAt": 1735630000000, "data": <与 IndexedDB 相同的原始数据> }
```
- `v`：格式版本，便于未来演进迁移；
- `savedAt`：最近同步时间戳（审计 + 未来合并决策）；
- 兼容读取旧版（无信封）的镜像文件（整体即数据）。

### 3.3 存储策略
- **写透式**：任何变更 → 内存先行 → 双通道落盘完成才返回（业务侧可 await）；
- **整体快照**：每类数据整表覆写（数据量小，简单可靠，无增量合并复杂度）；
- **写队列**：所有写操作串行执行，天然避免并发交错；单次失败不阻断后续。

## 四、数据读写、更新与同步机制

### 4.1 写入（dualWrite）
```
write(key, value):
  并行：IndexedDB.setItem(key, value)   │  文件: fs_save(key, 信封(value))
  → 仅当【两侧都失败】才抛错（业务层回滚内存，杜绝"幽灵数据"）
  → 单侧失败静默：另一侧仍完整可用，下次读取自动修复
```

### 4.2 读取（dualRead）
```
read(key):
  IndexedDB 有数据？ ──是──→ 返回 IndexedDB 数据；后台队列刷新文件镜像（保持一致）
        │否（空/报错）
  文件镜像有数据？ ──是──→ 解信封返回；后台队列回写 IndexedDB（自动修复主通道）
        │否
  返回 fallback（首次安装=空）
```

### 4.3 同步收敛规则
- 双通道成功写入 → 两侧一致；
- 单侧失败 → 下次读取经"刷新镜像/回写主通道"自动收敛；
- IndexedDB 长期损坏 → 文件镜像持续可用（读走镜像、写仍尝试双通道）；
- 文件镜像长期不可用 → IndexedDB 持续可用；
- 删除（清空本地数据）→ 双通道同步清除。

### 4.4 生命周期同步（后台清理优化）
- `pagehide` + `visibilitychange(hidden)` 钩子：冲刷写队列（尽力而为）；
- **可靠性不依赖钩子**：硬杀进程不保证触发任何 JS 回调，因此正确性建立在"每次变更立即双写完成"之上（见 4.1）；业务入口（新增任务等）均 await 落库完成后再反馈用户。

## 五、异常处理与数据恢复

| 场景 | 行为 |
|---|---|
| IndexedDB 为空（杀进程后） | 自动从文件镜像恢复，并回写 IndexedDB |
| IndexedDB 打开失败/损坏 | 捕获 → 走镜像读取；写入仍双通道尝试 |
| 文件镜像 JSON 损坏 | 解析失败按"无镜像"处理，回退 IndexedDB；不影响启动 |
| 双通道同时失败 | 写入抛错 → 业务层提示"保存失败"并回滚内存（不产生幽灵数据） |
| 首次安装 / 清空数据 | 双通道无数据 → 返回默认空态 |
| 镜像文件为旧格式（无信封） | 兼容读取，下次写入自动升级为信封格式 |
| 诊断 | 文件通道失败记入错误日志（设置页可导出），不打断主流程 |

## 六、实施步骤与测试

### 6.1 实施清单
1. **Rust**：`src-tauri/src/lib.rs` 新增 `fs_save / fs_load / fs_remove`（键白名单校验 + `app_data_dir` 落盘 + `Manager` trait 导入）；
2. **JS**：`src/utils/storage.js` 重构为可注入双写核心 `createDualStore`（写队列 / 信封 / 双读降级），4 类数据全部接入；生命周期冲刷钩子；
3. **业务入口加固**：`TasksView.handleAdd` await 落库；`useTasks.addTask` 双失败回滚内存；
4. **依赖**：新增 `@tauri-apps/api`（官方 Tauri JS 客户端，唯一新增依赖）。

### 6.2 单元 / 集成测试（tests/run-tests.mjs，49 项全过）
双写核心 10 项专项用例（注入内存假后端）：
- 写入两侧落盘、信封格式正确；
- 单侧失败静默 / 双侧失败抛错；
- IndexedDB 有数据优先 + 刷新镜像；
- IndexedDB 丢失 → 镜像恢复 + 回写；
- **IndexedDB 报错 → 镜像兜底（杀进程损坏场景）**；
- 旧格式镜像兼容；双侧无数据 → fallback；删除双侧清除；写队列串行与故障隔离。

### 6.3 真机验证清单（清理后台后数据可恢复）
1. 添加 3 个任务 → 完成 1 个番茄 → 设置暗色主题 → 切到 AI 页生成一次拆解；
2. 回桌面 → **从最近任务列表划掉应用**；
3. 重新打开：任务 3 个都在、统计有 1 条记录、主题仍是暗色、AI 拆解结果还在；
4. （进阶）连杀两次进程验证恢复路径；设置页"导出错误日志"可看到 storage-fs 相关记录（如有）。

### 6.4 已知边界
- 卸载应用 / 系统"清除数据"会删除全部本地数据（含文件镜像）——这是预期行为，方案定位是"进程级恢复"，不承诺卸载恢复；
- 网页预览（无 Tauri）仅 IndexedDB 单通道，行为与旧版一致。

## 七、v0.1.9 加固记录（系统化复检新增）

针对"本地保存失效"场景的系统化复检发现并修复 3 个遗留问题：

| # | 发现 | 修复 |
|---|---|---|
| 1 | **IndexedDB 无超时保护**：进程被杀后 leveldb 损坏可能使操作永久挂起（不 resolve 不 reject）→ 读卡死、界面无数据，表现为"保存失效" | `createDualStore` 新增 `idbTimeoutMs`（真实环境 3000ms）：IndexedDB 超时按"该侧不可用"处理——读走镜像恢复、写由镜像兜底、删镜像侧仍清除，应用永不卡死 |
| 2 | **网页预览日志污染**：非 Tauri 环境每次读写都 invoke 失败并写入错误日志（上限 200 条刷满），误导诊断 | `IS_TAURI` 检测（`__TAURI_INTERNALS__` 存在性）：非 Tauri 环境文件通道整体跳过，不 invoke、不记日志 |
| 3 | **AI 配置单通道**：`config.js` 直用 localStorage 存 API Key/useMock（唯一违规点），杀进程同样会丢 | 迁移双写：内存缓存（同步读语义不变）+ localStorage 同步层 + `ai_config` 键双写持久化 + 模块加载时自动恢复 |
| 4 | 附赠：无在途诊断手段 | 设置页新增**存储自检**按钮：`runStorageSelfCheck()` 用独立探针键（`__selfcheck__`，Rust 白名单放行）分别直读两通道并比对，写完即删，返回 `{ idbOk, fsOk, fsEnvelopeOk, errors }` |

**新增测试（53/53 全过）**：IndexedDB 永久挂起 → 超时降级镜像（读/写/删三条路径）；中文 + emoji + 特殊字符经 JSON 双通道往返无损。

**真机验证（v0.1.9）**：设置 → 数据管理 →「检测本地数据通道」应提示两通道正常；随后按 6.3 清单做杀进程恢复验证。
